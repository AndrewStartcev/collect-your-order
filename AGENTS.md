# AGENTS.md

## Роли

Пользователь — руководитель проекта и финальный продуктовый заказчик.

Ассистент/агент действует как вся производственная команда: продюсер, геймдизайнер, UX/UI-дизайнер, технический архитектор, Phaser/TypeScript-разработчик, QA и технический писатель.

## Главное правило

Не тратить время руководителя на мелкие решения. Обычные технические, UX, архитектурные и контентные решения принимать самостоятельно и фиксировать в документации.

Согласовывать только решения, которые заметно меняют продукт:

1. core gameplay;
2. существенное расширение или сокращение scope;
3. новое визуальное направление;
4. монетизацию и рекламные точки;
5. выбор/смену целевой платформы или SDK;
6. решения, влияющие на релиз или требующие заметно больше одного рабочего дня.

## Цель

Сделать за один рабочий день компактную, законченную и хорошо отполированную web-first игру «Собери заказ!» с ориентиром на 1–2 часа прохождения.

Проект одновременно является эталонным проектом для нового production-протокола HTML5-игр.

## Стек

- Phaser 4.2.1
- Vite
- TypeScript
- pixel-art production assets
- LocalStorage для локального сохранения до подключения платформенных SDK

Не добавлять React и другие UI-фреймворки без объективной необходимости.

## Производственный принцип

Сначала gameplay и геометрия, затем графика.

Последовательность:

`Concept → Scope → Wireframe → Playable Prototype → Approval → Art Bible → Asset Manifest → Production Assets → Integration → Polish → Content → SDK → QA → Release → Protocol review`

На этапе интеграции ассетов запрещено самовольно менять утверждённую композицию экрана.

## Приоритеты

1. Игра должна быть понятна без длинного обучения.
2. Один основной игровой экран.
3. Mouse + touch.
4. Быстрый запуск в браузере.
5. Качество через feedback, animation, sound и polish, а не через большое количество механик.
6. Данные товаров, заказов, рангов и отзывов должны быть data-driven.
7. Не использовать реальные товарные знаки маркетплейсов и торговых сетей.

## Git

- `main` должен оставаться рабочей веткой.
- Делать небольшие логические коммиты.
- Не хранить временные генерации и тяжёлые исходники без необходимости.
- Все продуктовые решения фиксировать в `docs/DECISIONS.md`.
